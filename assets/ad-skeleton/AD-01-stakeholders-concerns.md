# 干系人、关注点、视角与方面（42010 6.2–6.5）

> 本文内容整体为**从代码反推的假说**——真实干系人与其关注点的优先级在代码之外。
> 缺口声明见 [AD-00](AD-00-overview.md) §2，不在此重复。
> 结构化数据在 `ad-manifest.yaml`；本文只写论述与证据。追溯矩阵由
> `python3 scripts/check_coverage.py . --emit-matrix` 生成，不要手工维护。

## 1. 干系人（6.2）

42010 官方模板规定，下列八类**适用时必须识别**：users、operators、acquirers、owners、suppliers、developers、builders、maintainers。逐类核对结果：

| 类别 | 本系统中是谁 | 反推依据 | 置信度 |
|---|---|---|---|
| users | <…> | <路由表/命令定义位置> | <中> |
| operators | <…> | <运维端点/指标/配置项> | <中> |
| acquirers | <…或声明不适用及理由> | | |
| owners | <…> | <GOVERNANCE / LICENSE> | <低> |
| suppliers | <…> | <依赖清单> | <高> |
| developers | <…> | <CONTRIBUTING / git shortlog> | <高> |
| builders | <…> | <CI 配置> | <高> |
| maintainers | <…> | <CODEOWNERS / review 集中度> | <中> |

**不要因为「代码里看不到」就跳过 acquirers/owners。** 开源项目的治理约束（许可证兼容性、CLA、发布节奏、基金会规则）是真实的架构约束，常常解释了某些设计选择。

## 3. 关注点（6.4）

官方模板规定五类**必须考虑**：目的；架构对达成目的的适宜性；构建与部署可行性；全生命周期对干系人的风险与影响；如何维护与演进。

### 3.1 已识别的关注点

对每条给出**代码里的显式投入**作为证据——这是 concern 最强的证据形式。

| ID | 关注点 | 类别 | 代码中的证据 | 置信度 |
|---|---|---|---|---|
| C1 | <…> | purpose | <…> | |
| C2 | <…> | suitability | <…> | |
| C3 | <…> | feasibility | <…> | |
| C4 | <…> | risks | <…> | |
| C5 | <…> | evolution | <…> | |

取证参考：布隆过滤器/索引/缓存→查询延迟；feature gate→可裁剪性；重试/熔断→可用性；迁移脚本/版本协商→兼容性；审计日志/权限检查点→安全合规；压测目录→明确的性能目标。

### 3.2 否定结论（同样有价值）

代码里**完全没有投入**的方面，说明它不是这个项目的关注点：

- 【事实】<例：无任何多租户隔离代码，说明多租户不是本项目的关注点>（证据：<…>）

### 3.3 关于优先级

【缺口】关注点的优先级无法从代码恢复。代码只能显示「投入了多少」，不能显示「当时认为哪个更重要」——高投入也可能只是因为技术难度大。**本 AD 不给出排序**；需要优先级请询问维护者。

## 5. 方面（6.5）

aspect 用于**细化关注点与视图之间的追溯**——当一个关注点横跨多个视图时，用 aspect 把它切开，避免追溯矩阵变成全打勾。

| 方面 | 含义 | 用它切分的关注点 |
|---|---|---|
| 功能面 | 系统提供什么能力 | <C1> |
| 结构面 | 元素与依赖如何组织 | <C2, C3, C5> |
| 行为面 | 运行期如何交互 | <C4> |
| 信息面 | 数据如何组织与流动 | <C4> |

<示例：关注点「查询要快」横跨三个面——结构面（索引组织，落在信息视图）、
行为面（执行流水线，落在功能视图）、信息面（列式编码，落在信息视图）。>
