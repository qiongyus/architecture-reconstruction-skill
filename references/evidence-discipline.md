# 证据纪律：证据源、陷阱、置信度

## 标注约定

正文每条实质断言必须归入三类之一：

```markdown
【事实】<陈述>（`相对路径:行号`）

【推断】<陈述>（依据：<推理链>；置信度：高/中/低）

【缺口】<拿不到的东西>（原因：<为什么拿不到>；可能获取途径：<去哪问>）
```

文档头一次性声明证据基线，全文生效：

```markdown
> 依据版本：<branch> `<commit>`（<commit 日期>）｜分析日期：<date>
> 路径均相对于 <repo-root>。
> 证据等级：【事实】附 file:line；【推断】附推理链与置信度；【缺口】说明原因。
> 本 AD 为代码逆向重建，42010 的 6.2（干系人）、6.3（干系人视角）
> 与 6.10（决策理由）结构性不可从代码恢复，相关内容均为反推假说，
> 已逐条标注，不再逐节重复本声明。
```

**commit 锚点是必需的**：行号会漂移，没有 commit 的 `file:line` 过几个月就无法复核。

## 置信度判据

| 等级 | 判据 |
|---|---|
| **高** | 多个独立证据源一致指向同一结论；或存在唯一可能的解释（如某函数只有一个调用点） |
| **中** | 单一证据源支持，无反证；或存在其他解释但明显次要 |
| **低** | 从命名、目录结构、惯例推测；或证据间存在张力 |

**从命名和目录结构得出的结论上限是「低」**，除非有代码行为佐证。目录叫 `domain/` 不代表里面是领域逻辑。

## 证据源清单（按性价比排序）

### 1. 构建与依赖清单 —— 模块边界最硬的证据

`go.mod`、`Cargo.toml`（含 workspace members）、`package.json` + `pnpm-workspace.yaml`、`pyproject.toml`、`pom.xml`、`build.gradle`。

**为什么最硬**：构建系统强制执行这些边界，它们不可能"腐化到与现实不符"——编译不过就是不过。

**陷阱**：单体仓库里一个包可能包含多个逻辑模块；workspace 成员数不等于架构组件数。

### 2. 入口点 —— 圈定系统的全部功能面

`main()`、CLI 子命令注册表、HTTP 路由注册、消息消费者、定时任务、gRPC service 注册。

**为什么高价值**：从入口点出发做可达性分析，能圈出系统实际对外提供的全部能力，比从模块结构出发更完整。事件/接口/端点清单是逆向发现功能的首选起点。

**陷阱**：反射、依赖注入、插件动态加载会让静态可达性分析漏掉真实入口。

### 3. 目录与包结构 —— 只能当假设来源

**陷阱（重要）**：目录结构表达的是**当初的分解意图**，可能已经腐化。它是提出假说的来源，不是验证假说的依据。验证必须靠依赖关系。

### 4. 持久化 schema 与数据模型

migrations、ORM 模型定义、`.proto`、序列化结构体、磁盘文件格式常量。

**为什么高价值**：数据模型是最难逆转的架构决策，恢复价值最高。

### 5. 部署工件

Dockerfile、compose、k8s manifests、helm charts、systemd units、CI 发布流程。

**为什么高价值**：几乎可以直接翻译成部署视图，且是运行期拓扑的权威来源。

### 6. 配置面

环境变量、命令行 flag 定义、配置文件 schema、`.env.example`。

**为什么高价值**：暴露全部外部依赖与运行时开关；flag 的默认值常常隐含了性能与容量假设。

### 7. 测试 —— 前人写好的场景走查脚本

集成测试与 e2e 测试尤其有用：它们是可执行的、经过验证的场景说明。

**用法**：把关键集成测试当作「用例实现」读，能直接支撑行为视图。

### 8. 文字考古 —— 唯一能恢复 rationale 的来源

README、docs/、已有 ADR、设计提案（PEP / Rust RFC / KEP 这类正式渠道）、重大 PR 的讨论串、CHANGELOG、GOVERNANCE、CODEOWNERS。

**必须去读。** 这是唯一能把 6.10 从【缺口】变成【有据】的途径。

**陷阱**：官方文档可能滞后于代码。**反推的动机与官方文档表述矛盾时，以代码行为为准，并把两者差异记录为漂移证据**——不要悄悄采信其中一个。

### 9. git 历史

- **改动热点**：高频修改的文件≈架构敏感点。
- **共变分析**：总是一起改的文件≈隐性耦合，常常横跨"官方"模块边界——这类发现是漂移的强证据。
- **commit / PR 讨论**：少数能恢复 rationale 的来源。

**陷阱（务必检查）**：

- **浅克隆**：若 `.git/shallow` 存在，历史被截断。所有"很少改动/很稳定"的结论必须标注截断日期——否则「这个模块很稳定」可能只是历史没拉全。可用 `git fetch --deepen=N` 增量加深（一次性 `--unshallow` 在大仓库上容易因网络中断失败）。
- **squash 导入**：只有 1 个 commit 的仓库（vendored 快照、镜像）完全没有历史证据，直接声明该证据源不可用。
- **大规模格式化/重命名提交**会污染热点统计，识别并排除。

## 三种重建路线，交叉验证

出自 SAR 方法论（Symphony 方法区分 source view / target view / hypothetical view；Murphy & Notkin 的 reflexion model）。

### 自底向上（静态分析）

工具生成模块级依赖图，然后**聚类抽象**——把几百个包归并成 5–20 个构建块。工具只提供原料，聚类需要人的判断。

### 自顶向下（假设—验证）

先提出高层假设（"这看起来是 ports-and-adapters" / "这是插件内核架构"），把代码元素映射到假设模型，然后比对。reflexion model 的三类结果：

| 结果 | 含义 | 处理 |
|---|---|---|
| **convergence** | 假设模型与代码都有的关系 | 确认，可作【事实】 |
| **divergence** | 代码里有、假设模型里没有的关系 | 要么假设错，要么是架构违规——两者都是发现 |
| **absence** | 假设模型里有、代码里没有的关系 | 要么假设错，要么是未实现/已废弃 |

divergence 与 absence 都不是失败，是产出。

### 动态走查

真的把系统跑起来，用调试器、日志或 tracing 跟一遍关键路径。

**为什么必要**：静态图只能告诉你"谁可能调谁"，只有动态走查能告诉你"关键路径实际怎么走"。反射、DI、插件、异步分发在静态分析里都是盲区。

## 已知的系统性陷阱

| 陷阱 | 表现 | 对策 |
|---|---|---|
| 目录即架构 | 按目录名分层，实际依赖乱穿 | 用依赖分析验证每条边界声明 |
| 编造动机 | 处处「之所以这样设计是为了…」却无出处 | 改写为【缺口】或低置信度【推断】 |
| 图元素爆炸 | 把所有包都画进一张图 | 5–20 元素纪律；删任一元素都应损失大意思 |
| 采信滞后文档 | 照抄 README 的架构描述 | 以代码行为为准，差异记为漂移 |
| 浅克隆误判 | 「这个模块很稳定」 | 检查 `.git/shallow`，标注截断 |
| 忽略生成代码 | 把 `.pb.go`、`.qtpl.go` 当手写代码分析 | 识别生成物并排除，但记录生成链本身 |
| 忽略 vendor | 把 vendored 依赖计入自身规模 | 排除，但记录依赖关系 |
| 条件编译盲区 | 只看到默认 feature 下的结构 | 枚举 feature flag / build tag，说明各组合的结构差异 |

## 架构侵蚀与漂移

Perry & Wolf 的原始区分：

- **架构侵蚀（erosion）**：违背架构原则的修改累积，导致架构完整性受损。
- **架构漂移（drift）**：对架构的认知逐渐模糊、实现偏离原意，但未必违背具体原则。

对重建工作的含义：**你重建出的是 as-implemented，它与 as-designed/as-intended 的差异本身就是核心发现**。差异不是你分析得不对，是这个系统的真实状态。单列成节。
